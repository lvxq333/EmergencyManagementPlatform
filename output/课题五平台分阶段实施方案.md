# 课题五智能服务平台分阶段实施方案

> 建设目标：形成可持续接收监测数据、调用算法预测未来风险、自动预警并记录处置结果的平台。
> 开发现状：已有前端专题页面和 Java 用户管理基础，业务数据仍主要为模拟展示。
> 数据策略：仿真数据先跑通，真实数据可上传、可接入、可切换，历史记录可追溯。
> 推进方式：按阶段成果验收，不按日期或周数划分。完成本阶段自检后进入下一阶段。

## 目录

- 建设依据与范围
- 环境准备与现有工程整理
- 阶段一 基础管理与数据标准版
- 阶段二 实时数据接入与仿真回放版
- 阶段三 算法接入与未来风险预测版
- 阶段四 自动预警与处置闭环版
- 阶段五 综合展示与示范支撑版
- 阶段六 性能验证与交付验收版
- 实施优先级与责任分工

## 建设依据与范围

### 任务书要求如何落实

| 要求 | 平台应建设的能力 | 验证方式 |
|---|---|---|
| 感知、通信、评估、预警全链条 | 数据进入平台后自动处理、调用模型、产生风险结果和预警 | 一条事件从原始数据追溯到处置记录 |
| 不少于300个卫星导航基准站的数据综合处理能力 | 300个独立基准站的数据接入、预处理、计算调度、结果查询 | 约定数据格式、频率、单报文规模和处理任务后执行测试 |
| 不少于2000用户同时访问 | 认证会话、业务查询、推送和历史查询承载能力 | 按检测机构确认的业务负载压测 |
| 多源多模接入 | MQTT、HTTP接入，文件导入，字段及时间对齐，数据质量管理 | 正常、缺失、重复、乱序、异常、断线补传测试 |
| 风险识别与耦合评估 | 集成研究内容三与四成果，承载不少于三类灾种和三个管线系统的结果 | 单系统及耦合场景验证，保留模型及数据版本 |
| 多维可视化与用户管理 | 气象、浓度、位移等专题展示，历史回溯，权限和账户管控 | 页面、接口、跨角色和数据追溯测试 |
| 第三方测试和示范应用 | 配合测试与三处以上典型区域、累计不少于200公里管线的示范 | 第三方报告、应用证明或试用报告及相关材料 |

依据为《课题任务书-终版.pdf》第11、14—16、45—49页。300站是平台处理能力指标，不等于必须由个人建设300个实体站点；仿真测试能否作为正式检测输入，需要与检测机构确认。任务书的站网建设数量与平台处理能力数量属于不同指标。

**修正原规划中的数量口径：**“100个GNSS站加200个其他传感设备”不能替代“300个卫星导航基准站”。本方案将300个基准站测试数据源单独建设，气象、燃气、供水和供热终端按业务场景另行增加。仅生成300个站号也不代表达到综合处理能力要求。

**数据不足时的边界：**仿真和回放可用于开发、流程验证及约定条件下的性能测试；不能替代真实示范应用证明，也不能单独证明真实场景下预警准确率达到90%。算法精度验证由相应研究团队提供适用的数据、标签和方法，平台负责保留证据及统计接口。

### 当前可复用的基础

- `home.html` 和 `assets/dashboard.js` 已覆盖综合态势、数据接入、短临降雨、燃气、供水、供热、耦合研判、预警处置和历史分析。
- `backend-java` 已有认证、用户、角色、权限和简单风险概览模块。
- 已有 MySQL 表结构、Redis 配置、Nginx 配置和接口、部署说明。
- 当前专题分值、数据源状态和部分预警操作仍为前端模拟；历史导出尚有演示占位行为。
- Java 与 Node 部署路径同时存在，需要明确最终交付以哪套后端为准。本方案以现有 Java 工程作为后续主线。

当前状态依据本地代码检查，不能据此推断服务器已经完成相同功能。各阶段涉及的表、接口和目录均为拟新增或拟改造内容。

## 阶段一 基础管理与数据标准版

### 目标

平台能准确回答“哪个站点、哪个设备、哪个指标、什么单位、属于哪段管线、数据来自哪里”，并完成基础管理的持久化。

### 技术要点

| 技术点 | 要解决的问题 |
|---|---|
| 站点与设备分层建模 | 一个站点可能有多台设备，一台设备可能产生多个指标 |
| 数据字典与字段映射 | 不同单位提供的数据能够转换为统一格式 |
| 数据集版本与来源标识 | 仿真、上传、真实数据可区分和追溯 |
| JWT与服务端权限 | 修改配置和查看数据的权限由后端校验 |

### 第一步 建立基础档案

将“建设台账”落实为可查询、可新增、可编辑、可批量导入、可停用的设备与站点管理功能。

| 拟建表 | 核心字段或用途 |
|---|---|
| `station` | 站点编号、站点类型、位置、坐标参考系、区域、管理状态 |
| `device` | 设备编号、所属站点、设备类型、协议、预期上报周期、最后到达时间 |
| `metric_definition` | 指标编码、名称、标准单位、合理范围、采样要求 |
| `pipeline_segment` | 管段编号、管线类型、几何数据、长度及数据来源 |
| `device_pipeline_relation` | 设备与管段的对应关系 |
| `dataset` | 数据来源、上传人、版本、质量状态、使用范围 |
| `import_job` | 导入状态、成功数量、失败数量、错误文件位置 |

设备管理状态与通信状态分开记录。例如设备可以处于“启用但离线”，不能因没有数据就自动将设备停用。

### 第二步 定义统一数据格式

建议每条观测携带以下字段，最终由数据接口评审确认：

```json
{
  "messageId": "session-a-000001",
  "stationId": "GNSS-001",
  "deviceId": "DISP-001",
  "eventTime": "2030-01-01T00:00:00Z",
  "sourceType": "SIMULATED",
  "ingestMethod": "MQTT",
  "datasetId": "dataset-example-v1",
  "scenarioRunId": "run-example",
  "schemaVersion": "1",
  "metrics": [
    {"code": "vertical_displacement", "value": 1.62, "unit": "mm"}
  ]
}
```

示例时间仅用于说明字段格式，不是开发排期。`sourceType`记录真实、仿真或未知来源；`ingestMethod`记录MQTT、HTTP或文件。上传文件不一定是真实数据，来源还需单独填写。回放属于运行方式，不改变原数据来源。

平台生成接收时间和质量标识。还需明确甲烷体积分数与 `%LEL`、压力单位、位移参考基准、时区和坐标系，禁止仅修改显示标签完成单位转换。

### 第三步 实现导入与权限基础

先实现CSV模板、文件预览、字段匹配、逐行校验和错误报告，再扩展Excel及JSON。数据先进入暂存区，校验通过后发布为数据集版本；原文件保留，失败批次不能污染已启用数据集。

复用现有用户、角色体系，补充API权限。设备使用独立接入凭证；普通用户不得修改设备身份、数据源或预警规则。逐步完善账户禁用、登录失败锁定和配置审计。

### 拟新增接口

```text
GET/POST       /api/stations
GET/PUT       /api/stations/{id}
GET/POST       /api/devices
PATCH          /api/devices/{id}/status
GET            /api/metrics/definitions
POST           /api/datasets/import-jobs
GET            /api/datasets/import-jobs/{id}
GET            /api/datasets
POST           /api/datasets/{id}/publish
```

### 自检与阶段产出

- [ ] 站点、设备和管段关系可保存，刷新后不丢失。
- [ ] CSV合法行可导入，重复编号、未知单位和非法时间可定位到行。
- [ ] 查看员直接调用配置修改接口被拒绝。
- [ ] 真实、仿真及未知来源均能明确标识。
- [ ] 交付数据字典、表结构迁移、导入模板、管理接口和基础页面。

**阶段完成状态：基础数据有统一定义，真实文件到手即可校验和登记。**

## 阶段二 实时数据接入与仿真回放版

### 目标

让数据持续从站点进入平台，并被下游任务消费者读取。没有真实设备时，由仿真发送器通过同样的接入链路上报。

### 技术要点

| 技术点 | 要解决的问题 |
|---|---|
| MQTT和HTTP适配 | 兼容连续上报与批量提交 |
| 持久接收记录及重试任务 | 接入后下游故障时可恢复处理 |
| 去重与幂等 | 重复上报不重复产生有效观测和业务结果 |
| 消息队列与积压监测 | 算法与站点上报速度解耦 |
| 场景生成和事件时间回放 | 稳定复现异常发展过程 |

### 第一步 打通单站点接入

先实现单个仿真站点HTTP上报和原始消息落库，再加入MQTT消费适配。两种通道调用同一个校验与处理入口。

建议链路：

```text
真实设备或仿真发送器
→ MQTT或HTTP接入
→ 身份检查与原始消息持久化
→ 待处理任务
→ 校验标准化及监测存储
→ 算法任务队列
→ 占位消费者
```

MQTT传输确认并不等于平台已经落库或算法处理完成。HTTP只有在达到约定的持久化条件后才返回“已接收”；MQTT如需业务级确认，可由平台另发回执主题，区分“已接收”和“已处理”。

### 第二步 建立可恢复处理流程

新增 `ingest_message`、`processing_task`、`observation`或对应时序测量、`data_quality_event` 等记录。建议使用数据库接收记录和待投递任务共同提交的方式，再由后台投递到Streams，避免“数据库成功、队列失败”后任务永久消失。

- 每台设备消息使用稳定唯一ID，设备重启不能简单复用原序号。
- 消费成功并持久保存结果后才确认消费；失败保留状态并重试。
- 超过重试次数进入人工可见的失败任务列表，支持重新投递。
- 监测缺失、异常、重复、乱序和迟到，保留原始值及处理原因。
- 明确Redis持久化、任务恢复与队列保留策略，不能直接裁剪尚未处理的消息。
- 仿真发送器实现本地缓存和补传；真实设备补传能力需要设备方配合，平台只能检测和报告不可恢复的缺口。

### 第三步 建设300基准站测试数据源

单独构造至少300个卫星导航基准站的数据源；气象、燃气、供水、供热设备作为附加场景输入。明确基准站上报的是原始观测、定位结果还是位移解算结果，测试必须覆盖与任务书及检测方案一致的“综合处理”，不能只用少量标量代替所有原始数据处理。

从单站、少量站点逐步扩展到300站，记录报文规模和真实处理吞吐。如果每站每5秒发送一条消息，300站平均为60条消息每秒；这仅是负载计算示例，最终频率以设备及模型需求为准，还须覆盖集中上报和断线补传峰值。

### 第四步 建设场景与回放控制

场景包括正常运行、强降雨、燃气泄漏、供水爆漏、热力异常、多系统耦合，并附加离线、重复和延迟等通信故障场景。每个场景有固定种子、配置、运行编号、预期事件和起止过程。

仿真可生成监测值，但不能把场景“答案”直接作为预测结果。答案只用于评估；算法仍须通过正式输入接口处理监测序列。

回放支持启动、暂停、复位和倍速，使用独立事件时钟。倍速回放中的趋势窗口和持续时间按数据时间计算，不按电脑当前时间计算。

### 拟新增接口与页面

```text
POST           /api/ingest/observations
GET            /api/devices/{id}/latest
GET            /api/devices/{id}/observations
GET            /api/ingest/status
GET            /api/processing-tasks
POST           /api/processing-tasks/{id}/retry
GET            /api/scenarios
POST           /api/scenario-runs
POST           /api/scenario-runs/{id}/pause
POST           /api/scenario-runs/{id}/resume
POST           /api/scenario-runs/{id}/stop
```

数据接入页面显示真实统计的站点在线情况、最后到达时间、延迟、有效率、队列积压和失败原因；增加场景及回放控制，替换当前写死的完整率和在线状态。

### 自检与阶段产出

- [ ] 单站和300基准站数据能够持续接收、保存并被占位消费者处理。
- [ ] 重复消息不重复入有效观测，乱序数据有明确处理结果。
- [ ] 停止消费者后可观察积压，恢复后能继续处理。
- [ ] 重启服务后已确认接收的任务可恢复，故障期间缺口可统计。
- [ ] 场景可以复现，回放与真实运行数据不串流。
- [ ] 交付接入服务、仿真发送器、回放器、质量报告和故障测试记录。

**阶段完成状态：正式算法尚未到位时，数据也能持续送到算法入口前。**

## 阶段三 算法接入与未来风险预测版

### 目标

监测数据到达后自动组织成模型输入，计算当前状态和模型支持的未来风险，并保存可追溯结果。

### 技术要点

| 技术点 | 要解决的问题 |
|---|---|
| 滑动窗口与多源时间对齐 | 模型读取完整历史序列，而非只读最新一条数据 |
| Java与Python接口 | 将平台业务和算法实现分离 |
| 按站点或区域调度 | 控制推理频率及重复计算 |
| 版本化模型和结果 | 相同输入、不同算法版本可比较 |
| 数据新鲜度与模型可用性 | 防止把旧结果或无效结果显示为实时预测 |

### 第一步 冻结算法输入输出

为每个模型登记：输入指标、采样间隔、历史窗口、空间范围、最低数据完整率、支持预测时长、输出单位、版本和运行资源。

短临降雨、位移及管线风险不必使用相同输入窗口，也不能默认每个模型都能预测10、30、60分钟。界面仅提供当前模型实际支持的预测时长；模型不输出可靠概率时，置信度留空，不自行编造数值。

### 第二步 建立预测服务

建议在现有工程旁新增独立Python服务，目录如下，名称均为规划：

```text
平台开发01/
├── backend-java/
│   └── src/main/java/com/risk/platform/
│       ├── station/       # 站点与设备
│       ├── ingest/        # 接入与质量校验
│       ├── dataset/       # 上传和版本
│       ├── prediction/    # 窗口调度与算法客户端
│       ├── alert/         # 预警与规则
│       └── audit/         # 操作追溯
├── model-service/
│   ├── app.py             # 预测接口入口
│   ├── schemas/           # 输入输出定义
│   ├── preprocessing/     # 特征和时间对齐
│   ├── models/            # 基线和正式算法适配
│   └── evaluation/        # 指标评估
├── tools/simulator/       # 仿真与回放
├── datasets/templates/    # 上传模板
└── deploy/                # 部署配置
```

不必先拆成多个Maven模块，先按业务包扩展现有Java工程。模型训练与在线推理解耦，在线服务加载已训练模型；上传数据默认只触发校验和推理，不自动重训生产模型。

### 第三步 组装历史窗口并触发计算

```text
新观测到达 → 更新站点或区域窗口 → 校验完整度和新鲜度
→ 生成预测任务 → 模型推理 → 保存结果 → 发布结果事件
```

调度支持窗口周期触发和异常事件触发。相同对象、模型版本、数据版本和窗口终点使用同一任务标识防止重复。任务失败可重试，资源不足时合并尚未执行的旧实时任务，历史补算另走队列。

缺少历史窗口时显示“数据积累中”；关键指标缺失时显示“数据不足”，不能默认为低风险。补齐方法必须符合模型要求，保留补齐标记。历史补传可更新历史分析，但不能无条件作为当前告警触发源。

### 第四步 将预测结果结构化

结果至少包括 `predictionId`、对象、来源与运行编号、数据窗口、模型版本、生成时间、有效截止时间、当前风险、未来目标时刻和风险值、质量状态。预测目标时间必须相对于窗口终点明确计算。

新增 `model_registry`、`prediction_job`、`prediction_result`、`evaluation_run`。大体积格点、雷达图或模型输入文件保存到受控文件存储，数据库保留路径、校验值和元数据。

### 第五步 验证仿真与真实数据切换

初期使用可解释基线或明确标注的演示模型完成工程联调；算法团队交付正式模型后通过适配器替换。仿真结果标注“仿真输入预测”，真实模式标注数据新鲜度。

真实文件进入新数据集版本后，完成字段映射、质量检查和历史窗口准备，再运行同一预测接口。先在独立运行中对比结果，管理员确认后切换启用版本；保留旧版，不直接覆盖。真实模式断流时显示异常，不静默替换为仿真数据。

### 拟新增接口

```text
GET            /api/models
POST           /api/prediction-jobs
GET            /api/prediction-jobs/{id}
GET            /api/predictions/latest
GET            /api/predictions/{id}
POST           /api/evaluation-runs
POST           /model/predict             # 内部服务接口
GET            /model/health              # 内部服务状态
```

### 自检与阶段产出

- [ ] 连续上报后自动预测，不依赖用户刷新页面。
- [ ] 输入是历史数据窗口，未来目标时刻明确，无未来数据泄漏。
- [ ] 模型输出、数据来源和版本可追溯。
- [ ] 缺失窗口、模型超时、结果过期均有明确状态。
- [ ] 上传同格式数据能够运行，不需要重写页面和模型适配接口。
- [ ] 交付模型接口规范、至少一条实际推理链路和逐步覆盖三类风险的验证记录。

**阶段完成状态：平台能持续形成可解释、可追溯的预测结果。**

## 阶段四 自动预警与处置闭环版

### 目标

预测完成后自动评估预警条件，通知有权限的用户，并完成事件处理和审计。

### 实施步骤

1. 建立版本化规则：对象、指标、模型、等级、阈值、持续时间、恢复阈值、冷却时间及启用范围。
2. 支持当前观测超限和未来风险预测两类触发来源，详情页明确“已经异常”还是“预测可能异常”。
3. 增加重复合并、等级升级、恢复与解除逻辑。解除阈值可与触发阈值分开，避免状态反复跳变。
4. 每次规则执行保存输入、规则版本和命中原因；回放规则使用事件时间，真实告警要求数据和预测未过期。
5. 通过SSE或WebSocket推送已落库事件，断线重连后根据事件编号补查，实时连接本身不作为唯一记录。
6. 实现站内通知和API回调，记录回调尝试及重试结果。仿真运行的外部通知默认隔离，只投递测试目标。
7. 将当前前端确认、派单、关闭和规则编辑改为后端事务操作。

### 核心状态机

```text
待确认 → 已确认 → 已派单 → 处置中 → 已关闭
```

巡检员提交处置说明，授权人员关闭；误报关闭需要原因。后端验证当前状态、操作者权限和记录版本，禁止重复或越级流转。风险恢复与人工工单关闭分开记录：指标恢复不自动抹去未完成的处置任务。

新增 `alert_rule`、`alert_event`、`alert_transition`、`work_order`、`notification_delivery`。预警事件关联预测ID或观测ID、站点、管段、场景运行、规则版本和数据来源。

### 拟新增接口

```text
GET/POST       /api/alert-rules
PUT            /api/alert-rules/{id}
GET            /api/alerts
GET            /api/alerts/{id}
POST           /api/alerts/{id}/confirm
POST           /api/alerts/{id}/assign
POST           /api/alerts/{id}/start
POST           /api/alerts/{id}/close
GET            /api/alerts/{id}/timeline
GET            /api/events/stream
```

### 自检与阶段产出

- [ ] 场景异常自动触发预警，正常场景不会无依据地产生告警。
- [ ] 相同事件不会因页面刷新或消费重试反复新增。
- [ ] 断线重连后可补查告警，多个用户看到一致状态。
- [ ] 无权限操作、重复关闭和非法流转均被后端拒绝。
- [ ] 可由一条告警查到原始输入、预测结果、规则版本和全部处置记录。
- [ ] 交付完整业务闭环和自动化回归用例。

**阶段完成状态：具备“持续上报、自动预测、自动预警、处置留痕”的完整演示版本。**

## 阶段六 性能验证与交付验收版

### 目标

以可复现的测试证明平台能力，明确实际达到的指标和剩余外部条件，形成交付版本。

### 第一步 固定测试口径

在正式压测前，与负责人和检测机构确认300基准站的输入类型、频率、报文大小、模型负载、处理任务，以及2000用户的会话、查询、操作和推送组合。2000个注册账号、2000个空闲连接和2000个活跃用户请求不是同一口径。

### 第二步 测试业务与故障恢复

| 类别 | 必测场景 |
|---|---|
| 接入 | 正常、重复、乱序、非法单位、未知设备、延迟和批量补传 |
| 数据集 | 导入失败不污染正式数据；版本切换可回退；来源隔离 |
| 模型 | 窗口不足、推理超时、模型版本切换、结果过期和历史补算 |
| 预警 | 连续触发、重复合并、等级升级、恢复、非法流转与权限 |
| 通知 | 断线重连、回调失败、补查及重复投递 |
| 运维 | 接入服务、任务消费者、Redis和模型服务重启，备份恢复 |

### 第三步 测试吞吐与时效

同时记录发送、接收、拒绝、去重、待处理、成功和失败数量，使消息去向能够核对。300站持续写入时叠加用户查询、历史聚合和推送，观察CPU、内存、磁盘、队列积压和模型资源。

实时性分别测量：采集至接收、接收至任务触发、排队、推理、结果入库、告警推送。总时延包含窗口等待和模型调度等待，不能将这些从“数据到预警”时延中省略。跨设备时钟偏差也要记录。

原先建议的“2000并发持续30分钟、核心查询P95不超过2秒、错误率低于1%、连续运行72小时”可作为内部试测目标，不是任务书原文或已达到的结论。模型推理时延单独制定，并说明设备采样频率和预测更新周期。

### 第四步 算法效果与示范证据

平台区分工程测试和算法评估：前者验证数据能否稳定到达、任务是否完成、结果是否及时展示；后者使用独立测试集及真实或经认可的标签评估准确率、召回率、误报、漏报和提前量。回放时算法只能读取预测时刻以前的数据，场景答案不能进入模型特征。

应用示范、第三方报告和软件著作权登记分别跟踪负责人和状态。模拟数据可保障软件开发连续推进，但不能将尚未取得的正式证明标记为完成。

### 第五步 固化交付版本

- [ ] 阶段一至五功能回归通过，关键问题有关闭记录。
- [ ] 300基准站及2000用户测试场景、环境配置、脚本、原始记录和结论齐全。
- [ ] 依赖、数据库迁移、启动、停止、备份和恢复步骤可复现。
- [ ] 仿真发送器、场景配置、样例数据和演示录像归档。
- [ ] 接口文档、数据字典、用户手册、部署手册和测试报告齐全。
- [ ] 形成源码版本、发布包、文件校验值和回退说明。
- [ ] 第三方、软著及示范材料按实际进度登记，未完成项有责任方。

**阶段完成状态：软件具备交付条件，正式验收指标和外部证据按实际测试及取得情况确认。**

## 实施优先级与责任分工

### 推荐开发顺序

先做最小贯通路径，再增加规模和模型覆盖：

```text
单站档案与HTTP上报
→ 原始数据落库与占位消费
→ MQTT和可恢复任务
→ 仿真回放及300基准站负载
→ 一个模型自动推理
→ 一条预警及处置闭环
→ 扩展三类风险和三个管线系统
→ 完成专题页面与历史报告
→ 全链路测试和交付
```

阶段顺序表示依赖关系，不要求等所有站点和所有场景齐全才调通一个模型。可以用单站最小链路提前验证接口，但进入下一阶段验收前要补齐本阶段清单。

### 责任建议

| 责任角色 | 主要产出 |
|---|---|
| 平台开发 | 统一接入、数据治理、算法客户端、预警处置、页面、运维和工程测试 |
| 设备及数据提供方 | 设备协议、站点信息、采样频率、单位、补传能力及真实样例 |
| 研究内容三算法团队 | 单类型风险识别、预测模型、输入要求和效果评估资料 |
| 研究内容四算法团队 | 耦合评估、预警模型、解释字段及验证资料 |
| 示范承担方 | 场地、管线、试用记录、实际运行和应用证明 |
| 负责人及检测机构 | 范围确认、技术路线差异确认、检测口径与正式报告 |

以上为角色分工建议，不假定已有相应人力投入。单人实施时优先保证一条完整业务路径，模型研究和真实示范材料应保留明确外部接口。

### 每阶段统一完成规则

每阶段同时交付“能运行的功能、实际测试记录、必要说明文档”。界面存在但接口未实现、提示成功但未落库、仿真结果未标注来源，都不计为完成。

可延后的是框架迁移、微服务拆分、额外动画和任务书外的新功能。任务书已明确的功能若需要缩减，必须留下差异与确认记录。

最终需要演示的业务故事是：选择可追溯的数据源，连续上报监测数据，自动预测未来风险，产生与分发预警，完成处置，并用同一事件展示历史数据、模型依据和操作记录。获得真实数据后通过标准导入或实时接口进入这条相同流程。
